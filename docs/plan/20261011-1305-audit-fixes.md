## Context

Findings of the audit at commit 29e4540:

1. HIGH — `upsertUser` (`modules/account/auth/auth.service.ts`) rebinds any
   password-less account to a new IdP subject that presents the same
   username. A second identity with the same `preferred_username` takes the
   account over, admin role included.
2. MEDIUM — the asset signature message does not name the package, so an
   asset signed for one package verifies in another that shares the key.
3. MEDIUM — `scripts/sign-manifest.sh` and the example workflow sign
   whatever manifest the registry serves, on a schedule.
4. MEDIUM — behind the documented Traefik deployment every client shares one
   rate-limit bucket (`TRUST_PROXY` defaults to false).
5. MEDIUM — the registry's own update chain is unverified: no
   `trusted_keys`, unsigned releases, `bkhq/lode:latest`, no runtime digest.
6. MEDIUM — CI pulls `bkhq/lode:v0.0.2` while the real-client e2e suites
   need v0.0.5 and skip themselves.
7. LOW — the release job references actions by mutable tag.
8. LOW — a deleted published version id can be published again with other
   bytes.
9. LOW — a multipart upload checks its signing key at start only.

## Proposal

- (1) Rebind by username only a row whose `oauth_sub` is the single-user
  sentinel; any other row needs a verified email match. Regression test.
- (9) `completeUpload` refuses a signed upload whose key was revoked since
  the start. Regression test.
- (3) `sign-manifest.sh` signs a changed catalog only when the manifest's
  channels equal the `--expect <channel>=<version>` arguments; an unchanged
  catalog (the signature it carries is the one the key produces) is renewed
  without them. Example workflow and docs follow.
- (4) `.env.docker.example` sets `TRUST_PROXY` / `TRUSTED_PROXY_IPS`;
  deployment guide says why.
- (5) Pin `bkhq/lode` by digest in `Dockerfile` and `sign-release.sh`; add
  the bun runtime `sha256` to `deploy/lode.toml`.
- (6) CI pulls the version the suites use; in CI a missing lode binary fails
  the suite instead of skipping it.
- (7) Pin the release job's actions by commit.
- (2) Documentation only: one signing key per package; correct the claim in
  `docs/modules/registry.md`.

## Risks

- (1) An operator who relied on username rebinding between two IdPs loses
  it; the verified-email path remains.
- (3) Breaking for callers of `sign-manifest.sh` after a release step: they
  must pass `--expect`.
- (6) CI fails when Docker Hub is unreachable instead of warning.

## Scope

`apps/api` auth and registry upload services with tests, two scripts, one
example workflow, CI and release workflows, deployment files, docs.

## Alternatives

Not part of this plan, each needs a decision:

- (2) Binding the package into the signed message is a wire-format change
  shared with `bkhq/lode`.
- (5) `trusted_keys` with `require_signature = "enforce"` in
  `deploy/lode.toml`, and failing a release that has no signing key: the
  repository has no `LODE_SIGNING_KEY` secret yet.
- (8) Keeping a tombstone for a deleted published version needs a schema
  migration.
